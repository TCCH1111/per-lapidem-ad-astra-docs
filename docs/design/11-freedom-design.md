> 发起人明确要求：**更丰富、更好玩、更有自由度**，且四个方向全部要——微观管理自由、建造与工程自由、叙事自由、世界与规则自由。
> 这份文档回答一个具体问题：**这四个「自由」在机制上到底长什么样，以及代价是什么。**

---

## 1. 「自由度」在这里指什么

玩家说的「自由」通常混着四件不同的事。拆开定义，才不会做成「什么都想要、什么都不深」：

| 方向 | 一句话定义 | 玩家会说的话 | 反面（失败的样子） |
| --- | --- | --- | --- |
| **A · 微观管理自由** | 我可以精确干预到某一个人、某一件事 | 「我要那个铁匠现在就去修墙」 | 什么都要手动，累 |
| **B · 建造与工程自由** | 我可以造出系统没预设的东西，而且它们真的有用 | 「我造了水车，它真的带动了我的磨坊」 | 造了一堆没人用的布景 |
| **C · 叙事自由** | 每次开局长出的故事不一样，且我能影响它的风格 | 「这局我的医生疯了，因为他救不活他弟弟」 | 事件重复、无后果 |
| **D · 世界与规则自由** | 我能改写世界与规则本身 | 「我改了这个剧本的灾祸强度」 | 只有开发者能改，玩家只能忍 |

**四条自由共享一个约束（R-F0）**：**自由必须可撤回、可诊断、可渐进**。
- 可撤回：任何干预都能取消/回滚，不产生不可逆的误操作。
- 可诊断：玩家随时能看出「为什么没按我想的来」。
- 可渐进：新手用默认预设就能玩，高手再逐层展开。

## 2. 设计原则

| 编号 | 原则 | 说明 |
| --- | --- | --- |
| **R-F1** | 意图层是默认，微观控制是可选 | 默认体验是「划地/订单/排序/图案」四件套；不强制玩家点选每个居民。 |
| **R-F2** | 微观控制一律实现为**约束与偏好注入**，不替换基底规划器 | Folkways 的核心是「居民自己规划一天的工作」。我们的干预是给规划器**加约束**（谁能去哪、什么优先、什么时候不许干），而不是替它算路径。这是与上游架构和平共处的关键。 |
| **R-F3** | 任何自动化都有手动逃生口 | 系统卡住时，玩家永远能亲手做完（第一人称存在感），或强制指派。 |
| **R-F4** | 自由按「层」披露，不一次性倾倒 | L0 默认 → L1 策略 → L2 覆盖 → L3 接管（见 §3）。 |
| **R-F5** | 玩家造的东西必须能进入模拟 | 玩家建筑/机械必须可被居民识别、使用、维护、破坏；否则不进主线设计。 |
| **R-F6** | 叙事自由 = 系统给因果，玩家给风格 | 不提供剧情分支树；提供**叙述者风格 + 事件响应 + 记忆**。 |
| **R-F7** | 规则自由对三类人分级 | 玩家（配置/剧本）→ 数据包作者（JSON/Starlark）→ 程序作者（Java 插件）。任何一层都能改，且互不阻塞。 |
| **R-F8** | 自由度必须付出复杂度代价，并显式记账 | 每个新增可调项都消耗 UI/测试/文档预算；新增时必须回答「默认值是什么、谁需要它」。 |

## 3. 方向 A · 微观管理自由（四层模型）

> 这是与 Folkways 架构张力最大的方向，也是「更像环世界」的关键。它决定 UI 复杂度，必须在 M1 前定案（见 §8 OQ-F1）。

### 3.1 四层

| 层 | 名称 | 玩家能做什么 | 对应现实 | UI 入口 | 与基底规划器的关系 |
| --- | --- | --- | --- | --- | --- |
| **L0** | 默认意图层 | 划区块、下订单、排职业、画图案、放蓝图 | 环世界的「不设优先级」 | 殖民书 + 面板 | 完全交给基底 |
| **L1** | 策略层 | 作息表（Sleep/Work/Recreation）、禁限区（Allowed Area）、库存规则（Stock rule）、全局策略对象（备冬/警戒/集结） | Banished / RimWorld 的日程与区域 | 新增「计划」页 | **注入约束**：改变规划的输入，不改规划算法 |
| **L2** | 覆盖层 | 逐人 × 逐工种的允许/禁止与优先级（基底已有 1–4 档）、单次强制指派（「去把那面墙修好」）、个人指定（指定床/工具/餐食） | RimWorld 的手动优先级 | 居民详情页 + 世界内动作 | 注入**高权重偏好**；基底仍可拒绝（Refusal），拒绝要给出理由 |
| **L3** | 接管层 | 玩家亲自操作（挖、建、战斗、搬运）、暂停/倍速、命令模式（选中一队居民下达一次行动） | Minecraft 原生 + RTS 手感 | 世界内直接操作 | 居民让位；玩家的动作视为一次世界事件 |

### 3.2 交互与反馈要求（各层都要有）

| 要求 | 说明 |
| --- | --- |
| **可看见** | 任何已生效的约束必须在地图或面板上可见（例如禁限区半透明覆盖、优先级颜色）。 |
| **可取消** | 一次点击/一个按钮取消；框选批量取消。 |
| **可解释** | 当居民**没有**执行玩家的覆盖指令时，必须能回答「为什么」（被更高优先级占用？路径不可达？缺少工具？恐惧？）。这是 L2 能否被接受的分水岭。 |
| **不打扰** | L0 玩家永远不需要看到 L1–L3 的 UI（渐进披露）。 |

### 3.3 档位裁决：**已选 A-max**（2026-10-18，ADR-008）

| 方案 | 内容 | 优 | 劣 | 实现成本 |
| --- | --- | --- | --- | --- |
| **A-min** | 只做 L0 + L1 | 与基底哲学一致；UI 轻；风险低 | 「环世界玩家」会觉得不过瘾 | 低 |
| **A-mid** | L0 + L1 + L2 | 兼顾两类玩家；L2 的拒绝理由机制也让管理者受益 | 需要约束注入通道 + 诊断 UI | 中 |
| **A-max（已选）** | L0 + L1 + L2 + **L3（接管式指挥）** | 自由度最高，真正"随心所欲" | 相当于附带一个 RTS 控制层：UI/测试/平衡工作量显著上升 | 高 |

**A-max 的具体边界（写进 [PRD-005](../prd/PRD-005-intent-and-micro-control.md) §2.4）**：
- **L3 = 接管层**，包含 ① 战斗指挥（编队、警戒等级、指定防守点/撤退线）② **临时接管**（把某居民从规划器手里接管，直接下令执行一个动作，完成交还）。
- **不是**"永久剥夺居民自主"：接管必须**显式、临时、有代价**（被频繁摆布的居民产生情绪代价），危急需求可中断接管。
- **默认零接管**：玩家不用 L2/L3 时，行为与基底一致（可验证）。
- **不做**：通用脚本规则引擎、技能释放系统。

**为什么可以选 A-max**：我们**已 fork Folkways 本体**（[ADR-007](../00-charter.md)），引擎层的调度挂起、动作分类、设置项扩展都能直接改；插件路线下这三件事都做不到。

### 3.4 基底事实校正（来自 [r03](../research/03-front-and-interaction.md) §6，2026-10-17）

调研发现，基底的微观控制现状与我们的假设有出入，必须据此修正方案：

| 我们希望 | 基底现状（事实 + 出处） | 结论 |
| --- | --- | --- |
| 优先级 | **已有**：居民页对「工种 × 允许/禁止 × 优先级 1–4」可控（`ResidentsPage`）；`standing()` 用熟练度正负号表示允许/禁止 | L2 的优先级**只需扩展粒度与诊断**，不必从零做 |
| 手动单次指派 | **没有**：`Board.Act` 只有 Do/Edit/Open/Ping/Admit 五种动词，不存在「去做 X」的动作类型 | 必须新增「命令通道」（`Facing.act` 是现成的服务端落点，但缺动作分类）→ PRD-005 的核心工作量 |
| 作息表 / 排班 | **没有**：吃睡是自动需求（FULLNESS/SLEEPING meter），无任何时段/班次数据结构 | 全新 |
| 禁限区 | **没有**（仅有区域用途与巡逻路径） | 全新（可用 `Enrollment` + `Shape.Volume` 表达） |
| 暂停/倍速 | **没有**：只有原版 `/tick`；模组自身无时钟控制 | 依赖原版命令；我们可考虑提供 UI 入口（低风险） |
| 库存阈值 | 只有每容器一条 `Order(into, what, low, high, standing)` + 槽位范围；**无**全局配额、无类别储备、无区域专用库存 | 扩展点明确 |
| 图表/历史 | **几乎没有**：`MetricsPage` 只有实时库存网格 + 4 个数字；唯一时间窗是 `PastDay`（24000 tick、1200 分桶），且只当一行文字用 | 诊断/统计是**大缺口**（PRD-006 的价值所在） |
| 全局意图对象 | **没有**：玩家只能表达「区域用途 / 路径用途 / 订单 / 工种优先级」四样 | 「备冬/警戒/集结」等策略对象是新概念，需要新的数据模型 |
| 撤销 | **没有**（只有绘制中的取回/丢弃）；删除殖民地不可逆 | 我们的新交互必须自带撤销或确认 |
| 设置项类型 | `Schema.Setting` 是**密封**的（Items/Count/Choice/Flag）；区域设置窗最多 24 行 | **架构瓶颈**：条件式规则/曲线/排程都要先扩这个接口（触及 4 处代码） |
| UI 硬预算 | 每页 32 行 × 每行 4 动作；信息卡 8 行；Notice ≤4 参；Goods ≤8 | 「大表格 UI」必须用「列表 → 详情窗」模式 |
| 世界内操作门票 | 必须手持绑定的殖民书 | 新交互沿用，不做远程控制 |

**由此得出的实施顺序建议（写进 PRD-005）**：
1. 先扩 `Schema.Setting`（架构瓶颈，一次改到位）。
2. 再做禁限区 + 作息表（纯约束注入，风险低）。
3. 再做全局策略对象（新数据模型 + 页面）。
4. 最后做单次指派/命令通道（需要新动作分类与拒绝语义，风险最高，放最后）。

**R-F-API-5（新增）**：任何微观控制能力都必须能表达为基底的四类可写数据之一（区域/路径用途 + Schema、订单、工种许可与优先级、设置项）；**落在四类之外的，一律先论证是否值得动引擎**。

### 3.5 与基底的兼容性要求（技术约束，写进 PRD-005）

| 编号 | 要求 |
| --- | --- |
| R-F-API-1 | 约束注入优先复用基底已有的概念（区块/订单/职业/许可 Licence/拒绝 Refusal）；若需新概念，必须能表达为「过滤器」或「权重」。 |
| R-F-API-2 | 不新增独立的 tick 扫描；一切约束在规划时读取。 |
| R-F-API-3 | 玩家的覆盖指令必须**可以失败**，且失败要产生 Refusal 记录（这是叙事素材：居民会抱怨）。 |
| R-F-API-4 | 具体 API 挂钩点待 `docs/research/01-core-engine.md` 确认后补全（本文件需在阶段三前回填具体类名）。 |

## 4. 方向 B · 建造与工程自由

### 4.1 已有基础（Folkways 提供）

- 图案（Starlark 脚本）自动铺设：道路、拱桥、城墙、码头、矿场、采石场、铁路、拱廊、梯田。
- 蓝图（`blueprint` 货架）整体放置；部件（`piece`）供图案盖章。
- 玩家可以亲手建造，也可以把方块标记成殖民地设施（箱子/床/工作站）。

### 4.2 我们要补的自由

| 编号 | 能力 | 说明 | 依赖 |
| --- | --- | --- | --- |
| B1 | **玩家建筑可被居民使用** | 玩家用 Create 造的机械、用任意 mod 造的功能方块，可被登记为「工作站/存储/设施」，从而进入居民的规划 | 需要一套**登记机制**（类似基底把方块标记为殖民地一部分） |
| B2 | **地形改造进入主线** | 挖山、填海、梯田、运河、地下水治理，都是工程而非装饰 | 图案 + 区块 + 新的「地形工程」意图 |
| B3 | **机械的维护与操作** | 居民能操作/补给/维护机械（避免玩家成为唯一操作员） | Create 集成 + 新的工作类型 |
| B4 | **交通网络** | 铁路时刻表、站点、载客/载货（基底已有 rail 插件，需扩展） | 基底 rail |
| B5 | **垂直建筑与地下城** | 多层建筑、竖井、地下厅堂、通风与照明 | 建筑图案 + 温度/光照机制 |
| B6 | **可分享的设计** | 蓝图/图案可导出分享（社区生态） | 数据包货架 + 导出命令 |

### 4.3 关键设计判断

> **判断 1**：「玩家造的东西被用起来」是方向 B 与普通装饰 mod 的分界线。没有 B1，方向 B 就退化为普通建造游戏。
> **判断 2**：方向 B 的主要敌人不是技术，而是**性能**（大量自定义机械 + 大量居民寻路）。必须在 [性能预算](../pack/03-performance-budget.md) 里给「工程规模」设上限并做 LOD。

## 5. 方向 C · 叙事自由

### 5.1 三根支柱

| 支柱 | 机制 | 来源参考 |
| --- | --- | --- |
| **因果**（事情有来路） | 记忆系统：每个重要经历写入带情绪的 Memory；记忆影响情绪与关系；记忆会衰减但不消失 | DF + RimWorld |
| **关系**（人与人之间有账） | 好感/敌意/师徒/挚友/恋人/亲属/救命恩人/仇人；关系影响协作、争执、婚育、复仇 | RimWorld + DF |
| **可读**（故事能被读到） | 传说页：编年史、人物条目、家族树、墓志、事件年表 | DF Legends（简化版） |

### 5.2 玩家的「导演」能力（叙事自由 ≠ 剧情分支）

| 玩家能做的 | 玩家不能做的 |
| --- | --- |
| 选叙述者风格（和平/标准/残酷/自定义） | 直接指定「下一个事件是什么」 |
| 调事件频率、强度、冷却 | 取消已经发生的因果（已经结仇的势力不会因为读档而忘记） |
| 在事件中做选择（必须提供至少一条「不作为」路径） | 强制剧情路线 |
| 用剧本（Scenario）设定开局条件与初始张力 | 用剧情脚本编排固定故事 |
| 关掉某个模块（例如彻底关闭袭击） | 让世界在关闭模块后仍然产生同等张力（关闭即接受更平静） |

### 5.3 反重复机制（叙事自由的技术保障）

| 编号 | 机制 |
| --- | --- |
| R-N-1 | 事件权重包含「最近发生过的降权」，同类事件在冷却期内不重复 |
| R-N-2 | 事件模板带**角色槽位**（谁参与、谁受害、谁见证），同一模板在不同人身上产生不同故事 |
| R-N-3 | 事件结果写回记忆与关系，使下一次事件的上下文不同 |
| R-N-4 | 每局开局的世界参数（风土/势力/资源）不同，压力源不同 |
| R-N-5 | 传说页只记录**发生过**的事，不生成虚构历史（避免「AI 编故事」的空洞感） |

## 6. 方向 D · 世界与规则自由

### 6.1 三级改写能力（对应三类人）

| 级别 | 谁 | 能改什么 | 手段 | 是否热重载 |
| --- | --- | --- | --- | --- |
| **D1 玩家** | 普通玩家 | 难度、叙述者、经济系数、时代门槛、界面、按键 | `serverconfig` / `config` / 游戏内设置页 | 部分（重启/新世界） |
| **D2 数据包作者** | 会写 JSON/简单脚本的玩家 | 新需求、新记忆、新事件、新剧本、新时代门槛、新图案、新蓝图、新居民外观与模型、翻译 | 数据包货架（继承基底机制）+ Starlark | 是（`/reload`） |
| **D3 程序作者** | 会写 Java 的人 | 新插件、新居民种类、新工作类型、新 UI 页面、新集成 | 基底 `core/api`、`front/api` | 否（重载游戏） |

**R-F7-1**：任何新机制在实现时，必须明确它落在哪一级，并在 PRD 的「可改写性」章节登记。
**R-F7-2**：**默认目标是把新机制做成 D2 可改**（数据包驱动），只有无法数据化的部分才下沉到 D3。

### 6.2 剧本（Scenario）——世界规则自由的主要载体

| 项 | 内容 |
| --- | --- |
| 定义 | 一组「开局条件 + 初始状态 + 规则修正」的数据包条目 |
| 包含 | 起始人口与技能、起始物资、世界类型/风土、初始势力关系、事件池与权重、难度修正 |
| 玩家可见 | 新世界创建界面的「剧本」选择；也可在游戏中查看当前剧本 |
| 可扩展 | 数据包新增剧本；玩家可用模板复制修改 |
| 与难度解耦 | 难度（叙述者）与剧本正交：残酷剧本 + 和平叙述者 是合法组合 |

### 6.3 「世界本身」的自由

| 项 | 手段 |
| --- | --- |
| 地形与生物群系 | 整合包层面的世界生成 mod（Terralith / Tectonic 等，见 [mod 清单](../pack/01-modlist.md)） |
| 资源分布与丰度 | 世界类型 + 剧本参数 + 数据包矿脉定义 |
| 维度与远方 | 后期时代：地下世界、天空、星际（见 [时代进程](08-progression-and-ages.md)） |
| 势力与外交 | 世界地图抽象层 + 数据包势力定义 |
| 时间与季节 | 季节长度、年份循环、灾难频率（配置 + 剧本） |

## 7. 自由度的代价（必须记在账上）

| 代价 | 表现 | 缓解 |
| --- | --- | --- |
| UI 复杂度 | 页面变多、术语变多 | 渐进披露 + 预设（Profiles）+ 游戏内课程（Ponder） |
| 测试面爆炸 | 组合数增长（居民 × 约束 × 事件） | 只测交界点与不变量；用模糊测试守不变量 |
| 平衡难度 | 玩家可绕过压力（例如关掉袭击） | 明确「关掉即接受更平静」，不惩罚但也不假装 |
| 性能 | 约束读取、关系网、记忆增长 | 定期压缩（记忆合并、关系衰减）、按需计算 |
| 文档负担 | 每个可调项都要写文档 | R-F8：新增可调项必须记账，否则驳回 |

## 8. 验收标准

- [ ] AC-F1 新手不打开任何设置即可完整游玩 L0（默认体验成立）。
- [ ] AC-F2 玩家能在 L1 层用不超过 3 次点击建立一个作息表/禁限区/库存规则。
- [ ] AC-F3 玩家在 L2 层下达覆盖指令后，若居民拒绝，界面能给出至少一条可读原因。
- [ ] AC-F4 玩家用 Create 造的机械能被登记为工作站，并有居民主动去操作/补给（B1 成立）。
- [ ] AC-F5 一次 8 小时存档中，同一事件模板不出现两次相同上下文（R-N-1~R-N-4 成立）。
- [ ] AC-F6 传说页能列出本殖民地 ≥5 条真实事件条目，且每条可追溯到具体居民与时间。
- [ ] AC-F7 不改 Java，仅用数据包即可新增 1 个需求、1 个事件、1 个剧本（D2 成立）。
- [ ] AC-F8 四级自由每一级都能被安全地忽略（不产生错误或卡死）。
