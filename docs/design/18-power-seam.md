```
状态：设计（接缝契约）
负责人：规划者（agent）
最后更新：2026-11-06
上游依据：design/15-power-and-mechanical-residents.md（模型/阶梯/拓扑）、prd/PRD-011
前提：**本文件不实现能源网络**；它定义"以后实现能源时，哪些地方不需要重写"
```

---

## 1. 与 d17 同一条思路

气体（[d17](17-gas-seam.md)）和能源面对的是同一个问题：

> 机器"现在不能干活"这件事，**引擎已经有表达方式**——否决权。

所以能源的接缝**不是**在引擎里加"能源感知"，而是：

| 问题 | 谁回答 | 怎么接 |
| --- | --- | --- |
| 这一格的机器有没有电？ | **能源系统**（只读查询） | `PowerViews.energised(level, cell)` |
| 没电时能不能派人来干？ | **引擎**（既有否决权） | 注册一个 provider，理由 `NO_POWER` |
| 玩家怎么知道？ | **解释层**（既有） | 自动获得 |

---

## 2. 契约（只读，一个问题）

```java
/** 这个位置此刻有没有可用的动力。没有能源系统时返回 true（见 §3 的理由）。 */
public interface PowerViews {
    boolean energised(ServerLevel level, BlockPos cell);
}
```

**约束**：

| 约束 | 原因 |
| --- | --- |
| **只读布尔**，不返回焦耳/瓦特 | 数值属能源系统内部；引擎只需要"能不能干" |
| **不做网络遍历** | 每次派活都会问；网络解析由能源系统缓存 |
| **不可抛异常** | 没有能源系统时必须正常回答 |

---

## 3. 默认值：没有能源系统时返回 **true**

这一点与气体相反（气体默认 `CLEAN`），理由不同：

| | 气体 | 能源 |
| --- | --- | --- |
| 默认 | `breathable = true` | `energised = true` |
| 为什么 | 没有气体时空气当然能呼吸 | **先有能源系统，才有"需要电的机器"**；在它出现之前，任何询问都来自旧内容，不能因此被挡住 |

换句话说：**只有当建造了"需要电"的机器时，这个问题才会被问到**。所以默认 `true` 不会掩盖问题，只会避免"旧内容被新系统挡住"。

---

## 4. 机械族：不新开一套居民

d15 §7 把机械族当作"第二种居民"。代码侧**已经存在**这条路：`modulargolems` 模块就是让傀儡成为 `Body`。

**接缝纪律**（M3 期间必须遵守）：

| 规则 | 原因 |
| --- | --- |
| 任何新的居民种类必须走 `Resident` / `Body` / `Urges` | 否则排班、卡片、否决权、解释层全都要各写一套 |
| "机械族不需要吃饭"用**不产出该 urge** 表达 | 而不是给 `Urges` 加 `if (isGolem)` 分支 |
| 机械族的"电量"若要有 | 它是**需求**的一种（用 `Urge` 表达），不是新的引擎概念 |

---

## 5. 与气体的组合（已经验过的语义）

两个系统都会注册否决 provider，而 `Vetoes.of(colony)` 的组合语义是**任一拒绝即拒绝**（VERIFY-016/017 已测）。
所以"毒气 + 没电"同时成立时，任务不会被派出去；理由按 `Unassigned.Reason` 的阶梯取最具体的一个。

**不需要新的组合逻辑**——这是预埋里最省的部分。

---

## 6. 明确不做

| 不做 | 为什么 |
| --- | --- |
| 发电阶梯、储能、拓扑、线损 | d15 §3–§6 的模型，属 M3 实现 |
| 能源计量与账单 | 需要网络数据，现在没有 |
| 机械族的独立 AI | 走 `Urges` 即可；独立 AI 会绕开排班与解释层 |
| 任何 `PowerViews` 实现类 | 现在只定契约 |

---

## 7. 验收（M3 期间）

| 判据 | 怎么验 |
| --- | --- |
| 没有"这机器有电吗"散落在各处 | 搜 `energised(` 只出现在契约与注册点 |
| 无能源系统时零影响 | 既有 1482 条测试不退 |
| 能源实装时不用改引擎 | 注册一个 provider 即可生效（届时用测试证明） |
| 机械族没有平行系统 | 代码里不存在第二套"居民"概念 |
