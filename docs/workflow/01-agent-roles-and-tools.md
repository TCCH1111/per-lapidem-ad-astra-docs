# 角色分工与工具约定

```
状态：草稿
负责人：项目发起人
最后更新：2026-10-17
上游依据：docs/workflow/00-ai-workflow.md
```

> 参考文章的洞察：不同模型有不同性格——「善于沟通、有全局观但懒得做完、不在意技术细节」的适合做 Plan 与写文档；「专注细节、给方向能挖到底、不擅长沟通」的适合 Review 与深度实现。
> 本项目把它固化为**角色**（而非绑定某个具体模型），模型可以按可用性和成本随时替换。

## 1. 角色定义

| 角色 | 谁来做 | 输入 | 输出 | 完成定义（DoD） |
| --- | --- | --- | --- | --- |
| **人类（产品负责人）** | 项目发起人 | 一切 | 决策、PRD 定稿、验收判断 | 价值判断完成，范围收敛 |
| **调研者**（Researcher） | 独立 agent（可并行多个） | 一个问题 + 事实边界 | `docs/research/drafts/*.md` | 结论可验证、引用文件路径、列出不确定项 |
| **设计者**（Designer） | 侧重沟通与全局观的 agent | 调研稿 + 支柱 + 对标 | PRD 草稿（含 AC） | PRD 模板所有章节填满或显式标注「不适用」 |
| **规划者**（Planner） | 同上 | PRD 定稿 | 实现计划 + 测试清单 | 计划覆盖数据模型/API/i18n/性能/存档迁移 |
| **审查者**（Reviewer） | 侧重技术细节的 agent | 计划或 diff | 问题清单（按优先级） | 只报可复现、有依据的问题；给出修复建议 |
| **实现者**（Implementer） | 任一 agent（宜与规划者不同） | 计划 + PRD | 代码 + 测试 + i18n | 编译通过、测试全绿、无新增警告 |
| **验证者**（Verifier） | 另一 agent（不同视角） | diff + PRD 的 AC | 验收报告（逐条 AC 判定） | 每条 AC 有明确结论与证据 |
| **整合包维护者**（Packsmith） | agent | 候选 mod 清单 | 更新后的 `docs/pack/*` | 每个 mod 有版本、许可、兼容性验证结论 |

**分离原则 R-ROLE-1**：**规划者与审查者必须是不同的 agent 会话**（最好不同模型）；**实现者与验证者也必须是不同会话**。让同一个上下文既写又审，会掩盖它自己的错误。

## 2. 交接协议（Handoff Protocol）

> 长任务中上下文会丢、会压缩、会跨会话。**唯一可靠的交接面是文件**，不是对话。

**R-ROLE-2**：任何跨会话/跨角色的交接，必须落到文件里：

| 交接 | 必须写入的文件 | 最少内容 |
| --- | --- | --- |
| 调研 → 设计 | `docs/research/drafts/draft-*.md` | 方案、取舍、不确定项 |
| 设计 → 规划 | `docs/prd/PRD-NNN-*.md` | 术语、状态机、交互、规则、AC |
| 规划 → 实现 | `docs/prd/PRD-NNN-*.md` 的「测试计划」+ 独立计划文件（如 `docs/plans/PLAN-NNN-*.md`） | 改动清单、数据模型、测试清单、风险 |
| 实现 → 验证 | PR + 验收报告文件 `docs/reports/VERIFY-NNN-*.md` | 逐条 AC 判定 + 证据（命令输出/截图/日志） |
| 发布 → 后续 | `docs/prd/PRD-NNN-*.md` 的变更记录 | 状态、日期、一句话 |

**R-ROLE-3**：对话里说过但没写进文件的决策，视为**不存在**。发现这种情况时，先补文件，再继续。

## 3. 工具约定

### 3.1 Agent 编排

| 工具 | 用在哪 | 约定 |
| --- | --- | --- |
| **单任务直接做** | 1–2 个文件的改动、文档修订 | 不启动子代理，避免协调开销 |
| **`subagent`** | 并行调研、独立验证、独立审查 | 一次消息内并发启动多个；每个提示词必须自包含（子代理看不到主对话） |
| **`subagent_fork`** | 需要主对话上下文的后续工作（复审、延续分析） | 只在子任务确实依赖已有上下文时使用 |
| **`workflow`** | 大规模扇出（例如「对 60 个 mod 逐一验证兼容性」「对全部 PRD 做一致性审计」） | 仅当用户明确要求或任务确实需要大量并行时使用 |
| **长期目标（goal）** | 跨多轮的大目标 | 一个阶段一个目标；目标描述要可验收 |

### 3.2 版本控制

| 项 | 约定 |
| --- | --- |
| 主分支 | `main`（文档与整合包工程） |
| 特性分支 | `feat/<PRD编号>-<短名>`、`docs/<主题>`、`pack/<主题>` |
| 提交信息 | `type(scope): summary`（继承基底约定） |
| 大改动 | 先合并文档提交，再合并代码提交（便于回溯「先改文档」） |
| worktree | 主 feature 实现期间，用 2 个左右 worktree 并行正交小任务；共享依赖目录避免重复下载 |

### 3.3 目录与产物约定

| 产物 | 位置 | 是否入库 |
| --- | --- | --- |
| 设计文档 / PRD / 计划 / 报告 | `docs/**` | 入库 |
| 调研草稿 | `docs/research/drafts/**` | 入库（用完即弃，可归档） |
| 整合包工程 | `pack/**` | 入库 |
| 自研插件源码 | `plugins/**` | 入库 |
| 基底只读参考 | `reference/**` | **不入库**（升级时整体替换；用脚本/说明记录来源 commit） |
| 测试与截图产物 | `tests/out/**` | 不入库 |

**R-ROLE-4**：`reference/` 必须记录来源与 commit（写入 `reference/README.md`），否则无法判断我们的插件是针对哪个版本写的。

### 3.4 上下文卫生

| 规则 | 说明 |
| --- | --- |
| 长任务先建 goal | 跨多轮的目标准确记录，避免反复确认 |
| 多步任务先建 todo | 让协作者（人）看到进度 |
| 不把大段代码粘进对话 | 需要引用就写文件路径 + 行号 |
| 每完成一个阶段就落文件 | 上下文丢失后可恢复 |
| 一次只推进一个 PRD | 并行只用于调研与验证，不用于同时实现多个复杂系统 |

## 4. 各阶段推荐的角色组合

| 阶段 | 主导 | 参与 | 禁止 |
| --- | --- | --- | --- |
| 一 · 发散需求 | 调研者（多个并行） | 设计者 | 人类不参与细节 |
| 二 · 写 PRD | **人类** | 设计者（起草与细化） | 由实现者单独写 PRD |
| 三 · Plan + Review | 规划者 | 审查者（≥1，不同会话） | 跳过 review |
| 四 · 实现 | 实现者 | 人类（并行处理正交小任务） | 实现者顺手改 PRD |
| 五 · 测试 | 实现者自查 + 验证者 | 人类（功能验收） | 只看测试绿不看 AC |
| 六 · 人工 Review | **人类** | 审查者（生成清单） | 全权交给 agent 判断「好玩」 |

## 5. 升级与维护流程（针对基底 Folkways）

| 触发 | 动作 |
| --- | --- |
| 上游发布新版本 | 1) 拉取到新的 `reference/folkways-<版本>/`；2) 重跑 `docs/research/01~05` 的调研（可只跑差异）；3) 检查我们使用的 API 是否变更；4) 更新 `docs/research/06-gap-analysis.md`；5) 决定是否升级整合包基线 |
| 上游 API 变更 | 记录到 `docs/plans/` 的「上游变更应对」；评估插件改动量；必要时锁定旧版本 |
| 上游停止维护 | 触发决策：迁移到自维护 fork（重新评估 ADR-001） |
