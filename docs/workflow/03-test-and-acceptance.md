## 1. 原则

| 编号 | 原则 |
| --- | --- |
| T1 | **验收标准先于实现**。PRD 的每条 AC 必须能判定真假，并尽量能翻译成测试。 |
| T2 | **测试关注交界点，不关注内部细节**。API 边界、存档读写、状态迁移、跨系统影响优先。 |
| T3 | **能自动化的必须自动化**；不能自动化的写成逐条人工检查清单，不允许「感觉没问题」。 |
| T4 | **近乎零成本的测试宁滥勿缺**：写得不好可以随时删掉重写，但没有测试的代码不允许合并。 |
| T5 | **性能是验收项**，不是事后优化。每个新增系统必须给出 tick 预算估算并在基准场景验证。 |
| T6 | **整合包本身也是被测对象**：安装、启动、mod 兼容、崩溃、**双语文案**、存档、卸载。 |

## 2. 平台现实（必须先知道）

| 事实 | 影响 |
| --- | --- |
| 基底 Folkways 的自动化测试驱动 **Blockwright**（真实 Minecraft 客户端/服务端）**仅支持 Linux x64** | Windows 开发机**不能**跑 e2e / 视觉 / 基准套件 |
| Windows 可以跑：Gradle 构建、NeoForge 游戏测试（`runGameTestServer`，若无需 GPU）、Node 单元测试、i18n 检查、类型检查 | 日常开发回路必须建立在这些上面 |
| 需要图形界面的测试（客户端、截图、录像）需要 GPU 与显示 | 只能在 Linux 机器 / WSL2 + 显示 / CI 上跑 |

**因此我们的分层策略**：

```
┌─ 层 0：Windows 本机 · 每次保存都跑（秒级）
│    构建编译 · Node 单元测试 · i18n 检查 · 类型检查 · 资源校验
├─ 层 1：Windows 本机 · 每个 PRD 跑（分钟级）
│    NeoForge 游戏测试（无头 server）· 存档往返测试 · 纯逻辑无头测试
├─ 层 2：Linux/WSL2/CI · 每个里程碑跑（十分钟~小时级）
│    e2e（真实客户端）· 视觉回归 · 性能基准 · 模糊测试
└─ 层 3：人类 · 每个 PRD 与每个里程碑（不可替代）
     玩法手感 · 叙事质量 · 平衡 · 「好不好玩」
```

**R-T-1**：层 0 与层 1 必须能在没有网络、没有 GPU 的 Windows 机器上通过；否则日常开发会被卡死。

### 2.1 基底的实际测试体量（用于估算我们自己的成本）

来自对 `reference/folkways-master` 的调研（[r05](../research/05-engineering-and-tooling.md) §2）：

| 层 | 基底的实际规模 | 耗时量级 | Windows |
| --- | --- | --- | --- |
| 静态 lint | `gradlew check`（Tab / 行尾空白） | 秒级 | ✅ |
| 类型检查 | 6 个 TS suite | 十几秒~分钟 | ✅ |
| 单元（无游戏） | 15 个 `*.test.ts` | 秒级 | ✅ |
| i18n | 179 行检查：上游既有键四语言不回归；**新增键 `zh_cn` + `en_us` 键集**、占位符、pattern 字典、notice/refusal 枚举 | 秒级 | ✅ |
| 游戏内单测 | **488 个 `@GameTest`**（85 个类） | 分钟级 | ⚠️ 理论可，仓库未验证 |
| 端到端 | **44 个 spec ≈ 79 个 test**，每个 = 一对真实客户端+服务端 | 15~20 分钟（并行） | ❌ |
| 视觉 | 12 个 spec（截图/录屏/布局 lint/窗口覆盖门禁） | 20 分钟/spec | ❌ |
| 基准 | 1 个场景（**400 居民**大城镇） | 60 分钟 + ≥25 分钟运行 | ❌ |
| 模糊 | 3 个 target（build / economy / paths），8 plot/服务器 + 分片 + 收缩 | 10 分钟 + 运行时长 | ❌ |
| 宣传片 | 10 个 take | 60 分钟/个 | ❌ |

**重要事实（我们必须弥补的缺口）**：基底自带的 CI **只跑构建 / 类型检查 / 单元测试**，488 个游戏测试与 44 个 e2e **完全不在流水线上**（[r05](../research/05-engineering-and-tooling.md) §1.5）。这意味着「游戏内行为」在这套工程里是靠人工在本地跑的。
→ 我们的策略：**至少把 `runGameTestServer`（层 1）纳入 CI**，这是我们相对基底能立刻取得的工程优势。

**R-T-4（新增）**：我们的 CI 必须至少覆盖层 0 + 层 1；层 2 允许按里程碑手工触发（受 Linux/GPU 约束）。

## 3. 测试类型清单（本项目）

| 层 | 类型 | 跑什么 | 覆盖的风险 | 频率 |
| --- | --- | --- | --- | --- |
| 0 | 编译/静态检查 | 无 tab、无行尾空白、编译错误、警告 | 低级错误、风格漂移 | 每次改动 |
| 0 | 单元测试（无游戏） | 纯函数/纯逻辑（例如需求数值曲线、事件权重计算、术语解析） | 逻辑错误 | 每次改动 |
| 0 | i18n 检查 | 上游既有键四语言不回归、**新增键双语完整**、参数一致、notice/refusal 覆盖 | 翻译缺失/参数错位 | 每次改动 |
| 0 | 类型检查 | 工具链 TS 脚本 | 工具链错误 | 每次改动 |
| 1 | 游戏测试（gametest） | 需要在真实注册表/世界中验证的行为（方块、实体、数据包加载） | 集成错误、注册错误 | 每个 PRD |
| 1 | 存档往返 | 保存 → 加载 → 状态一致；旧存档迁移 | 数据丢失、迁移崩溃 | 每个涉及持久化的 PRD |
| 2 | e2e（真实客户端） | 玩家可见流程（放置、划地、面板操作、袭击、事件触发） | 端到端断裂 | 每个里程碑 |
| 2 | 视觉回归 | 面板布局、世界内视觉、图案预览 | UI 回归 | 每个里程碑 |
| 2 | 性能基准 | 大殖民地场景（人数 × 时间）的 tick 时间与内存 | 性能退化 | 每个里程碑 + 每个重系统 |
| 2 | 模糊测试 | 规划器/旅行/建造在随机输入下的不变量 | 罕见崩溃、死锁、状态污染 | 每个里程碑 |
| 3 | 人工验收 | PRD 的 AC、手感、平衡、叙事 | 唯一能判定「好玩」的方式 | 每个 PRD |

## 4. 自动化验收的组织方式

### 4.1 命名与位置（沿用基底风格）

| 内容 | 位置 |
| --- | --- |
| 游戏测试 | `plugins/src/gametest/java/...`（自研插件） |
| 单元测试（无游戏） | 工具链目录下的 `*.test.ts` 或 Java 侧纯逻辑测试 |
| e2e | `tests/e2e/*.spec.ts` |
| 视觉 | `tests/visual/*.spec.ts` |
| 基准 | `tests/bench/*.bench.ts` |
| 模糊 | `tests/fuzz/*.fuzz.ts` |
| 人工清单 | `docs/reports/MANUAL-<PRD编号>-<短名>.md` |

### 4.2 每个 PRD 的测试计划模板（已包含在 PRD 模板第 17 节）

| 字段 | 要求 |
| --- | --- |
| 测试名 | 动词 + 对象 + 预期（例如「居民在饥饿 ≥ 阈值时优先寻找食物」） |
| 类型 | 单元 / gametest / e2e / 视觉 / 基准 / 人工 |
| 覆盖的 AC | 指向 AC 编号 |
| 是否可在 Windows 跑 | 是 / 否（否则标注需要 Linux runner） |

**R-T-2**：每个 P0 系统的 PRD，其测试计划里至少要有 1 条**跨系统交界**测试（例如「情绪崩溃 → 劳动分配 → 物流中断」这条链）。

## 6. 性能验收

**基准场景**（在 Linux runner 上跑，结果存档对比）：

| 场景 | 配置 | 采样指标 |
| --- | --- | --- |
| 小型 | 10 居民，无袭击，白天 | 平均/95 分位 tick 时间 |
| 中型 | 30 居民，含农牧渔、物流、建造 | 同上 + 每居民均摊 |
| 大型 | 60 居民 + 2 名玩家 + 袭击进行中 | 同上 + 内存 + 实体数 + 网络包 |
| 极端 | 120 居民（压力测试，允许 TPS < 20） | 找出第一瓶颈 |

**通过阈值**（对应 [项目章程](../00-charter.md) 的 S5）：中型与大型场景服务端 TPS ≥ 20。

**R-T-3**：任何 PRD 若其性能估算超过总预算的 10%，必须在 PRD 中写明「预算来自哪里（削减了什么）」。

## 7. 存档兼容性验收

| 检查项 | 方法 | 通过标准 |
| --- | --- | --- |
| 往返 | 保存 → 退出 → 进入 | 状态、数值、关系、编年史完全一致 |
| 版本迁移 | 旧版本存档 → 新版本 | 无崩溃、无静默丢数据；迁移有日志 |
| 卸载 mod | 存档 → 移除自研插件 → 进入 | 可进入（允许丢失本 mod 内容），不崩溃 |
| 降级 | 新存档 → 旧版本 mod | 明确拒绝加载并给出可读提示（而非崩溃） |
| 大规模 | 30 小时基准存档 | 加载时间与内存可接受 |

## 8. 整合包特有验收

| 项 | 检查 | 通过标准 |
| --- | --- | --- |
| 安装 | 新机器按安装指南操作 | 20 分钟内进入游戏（对齐 S6） |
| 启动 | 首次启动、二次启动 | 无崩溃、无缺失依赖提示 |
| mod 兼容矩阵 | 每个 mod 与 Folkways 及彼此 | 记录在 `docs/pack/01-modlist.md` 的兼容性列 |
| 客户端/服务端差异 | 单机 + 专用服务器 | 一致行为（除客户端视觉） |
| 语言 | 切换 zh_cn / en_us（新增键）；**回归**：zh_hk / zh_tw 下既有键无缺失、无错位参数 |
| 性能 | 默认配置 + 推荐配置 | 达成性能预算 |
| 更新 | 从上一版本升级存档与配置 | 无阻塞性错误 |
