# 提示词模板库

```
状态：草稿
负责人：项目发起人
最后更新：2026-10-17
上游依据：docs/workflow/00-ai-workflow.md、参考文章《我的工作流》与《踩坑总结和建议》
```

> 使用方式：复制模板 → 把 `【】` 里的内容替换成具体对象 → 发给 agent。
> **每个模板都假设「不管的可以问」**：保留最后一行，鼓励 agent 提问而不是猜测。

---

## P1 · 阶段一：发散需求（写方案，不写技术）

**时机**：新系统立项，方向模糊。

```
我在设计【系统名】。

背景：这是一个以 Folkways 为基底的 Minecraft 殖民地模拟整合包（对标矮人要塞/希克斯之歌/环世界/石炉），
设计支柱见 docs/design/01-vision-and-pillars.md。

现有事实（必读，不要臆造）：
- 【列出 Folkways 已提供的相关能力，引用 docs/research/01-core-engine.md 或 02-plugin-inventory.md 的具体章节】
- 相关设计纲要：docs/design/【NN-xxx.md】
- 相关对标机制：docs/design/02-benchmark.md 第【N】章第【编号】条

请你：
1. 调研同类游戏（矮人要塞 / 希克斯之歌 / 环世界 / 石炉 / 以及 MC 生态的同类 mod）里类似系统怎么做，
   列出它们的机制与取舍；
2. 扩充并细化功能，描述玩家视角下的具体表现（玩家看到什么、能做什么、会遇到什么）；
3. 给我 3 个**纯游戏逻辑**设计方案（不要技术实现、不要代码、不要文件路径），写成 markdown 文件，
   存到 docs/research/drafts/draft-【系统名】-【YYYYMMDD】.md；
4. 明确写出三个方案的取舍差异，以及你不确定、需要我决策的地方。

有不懂的可以问我。
```

**验收**：3 个方案可比较；无技术内容；不确定项被显式列出。

## P2 · 阶段二：写 / 细化 PRD

**时机**：方案已选定，需要写成可实现的规格。

```
请按 docs/prd/00-prd-template.md 的结构，把【方案 N】写成 PRD 草稿，
存为 docs/prd/PRD-【NNN】-【短名】.md。

要求：
1. 所有章节都要填满，或显式写「不适用」——不允许留空；
2. 术语必须与 docs/design/03-glossary.md 一致，并做「与既有术语的冲突检查」
   （特别注意 Folkways 已有的 Zone / Order / Vocation / Doing / Refusal 等词）；
3. 验收检查（第 16 节）每一条都要能判定真假，并标注「可自动化 / 需人工」；
4. 数值配置（第 9.6 节）给出默认值与范围，并标注哪些可被数据包覆盖；
5. 明确写「非目标」（本次不做），至少 3 条；
6. 只依赖 Folkways 的 core/api 与 front/api；如果必须触及内部实现，显式标注风险；
7. 第 13 节给出性能预算估算（每 tick 成本、内存、网络包）；
8. 第 18 节如实列出你还不能定的问题。

有不懂的可以问我，不要自己替我做产品判断。
```

**验收**：模板无空章节；AC 可判定；「本次不做」非空。

## P3 · 阶段三：Plan + TDD

**时机**：PRD 已定稿。

```
阅读 docs/prd/PRD-【NNN】-【短名】.md，给出实现方案，并且用 TDD 的方式实现。

要求计划中包含：
1. 改动清单（模块 / 文件 / 数据包货架），引用具体路径；
2. 数据模型与存档影响（新字段？是否需要迁移？迁移策略？）；
3. 与 Folkways 公共 API 的交互点（引用 core/api、front/api 的具体类）；
4. 网络同步与客户端表现（若涉及 UI）；
5. i18n：需要新增的**双语键（`zh_cn` + `en_us`）**；
6. 性能成本估算与依据；
7. **测试清单：先写哪些测试、分别覆盖哪条 AC**（这是硬要求）；
8. 风险与回滚方式。

先只给我计划，不要动代码。有不懂的可以问我。
```

**然后**（同一个会话或另一个会话）：

```
请扮演严格的实现审查者，审查上面这份计划。只报告**可复现、有依据**的问题，按严重度排序：
1. 与 PRD 的偏离（引用 PRD 章节）；
2. 与 Folkways API 能力边界不符的地方（引用 docs/research/04-content-and-modding.md）；
3. 存档兼容与迁移风险；
4. 性能风险（每 tick 遍历、分配、网络包）；
5. 测试覆盖缺口（特别是跨系统交界点）；
6. 遗漏的边界情况（断线、区块卸载、居民死亡、并发玩家）。
每条给出具体修改建议。
```

**再做**：让规划者按审查意见修复，重复约 2 轮，最后人类扫一眼。

## P4 · 阶段四：实现

```
按最终计划实现，遵循以下约定：
- 只依赖 Folkways 的 core/api 与 front/api；
- 提交信息用 type(scope): summary；
- 玩家可见文本**新增键为双语（en_us / zh_cn）**（上游既有键的四语言文件保留不动），翻译文本在到达客户端前保持 Component；
- 无 tab、无行尾空白；
- 每完成一部分就跑一次本机可跑的测试（编译 / 单元 / i18n / 类型检查），不要攒到最后；
- 不修改 PRD 未覆盖的行为；实现中发现设计问题，先告诉我，不要自己改方向。

有不懂的可以问我。
```

## P5 · 阶段五：代码侧 review

```
请 review 当前分支相对 main 的全部改动，重点找**破坏性**问题，按严重度排序：
1. 崩溃/异常路径（null、越界、并发、客户端/服务端不同步）；
2. 存档写入与读取的一致性、迁移遗漏；
3. 每 tick 的性能退化（不必要的遍历、装箱、流式操作、网络包）；
4. 与 Folkways 既有机制冲突或重复实现；
5. 缺失的拒绝理由（Refusal）/ 玩家反馈；
6. 重复代码与可维护性问题。
不要纠结风格细节。每条给出文件:行号与具体修法。
```

## P5b · 阶段五：功能侧验收清单

```
请根据 docs/prd/PRD-【NNN】-【短名】.md 的「验收检查」，生成一份**人工验收清单**，
存为 docs/reports/MANUAL-【NNN】-【短名】.md。

要求：
1. 按 AC 编号逐条列出，每条给出：前置条件、操作步骤、预期结果、如何判定通过；
2. 区分「可自动化」（说明用哪个测试覆盖）与「必须人工」；
3. 补充 PRD 未写但你需要验证的边界情况（断线、区块卸载、多人并发、极端数值）；
4. 给出 3 个「讲故事」的观察点：这个系统应该产生什么戏剧性时刻。
```

## P6 · 阶段六：人工 review 清单

```
对比当前分支和 main 的全部变动，我准备做人工 review。
请给我一个 review 清单，按优先级排序，并说明每条为什么值得看。

注意：
1. git diff 会很大，请灵活处理（按系统分组，不要逐行罗列）；
2. 重点标注：主干架构、系统之间的交互点、存档格式、玩家可见规则、性能敏感路径；
3. 对每条给出「要看什么」与「什么情况算有问题」；
4. 最后给出一个 5 分钟快速通道（如果我只有 5 分钟，应该看哪三条）。
```

## P7 · 收尾：补单元测试

```
针对本次全部修改，设计测试，并确保测试：
1. 简洁、可维护；
2. 只覆盖关键逻辑；
3. 关注系统交界点（API 边界、存档读写、状态迁移、跨系统影响），而不是内部实现细节。
列出每条测试覆盖哪条 AC。有不懂的可以问我。
```

## P8 · 文档与代码漂移检测

```
请对【系统名】做一次文档-代码一致性审计。

输入：docs/prd/PRD-【NNN】-【短名】.md 与实现代码【路径/模块】。

输出一张表，三列：
1. 文档写了但代码没实现（缺口，引用 PRD 章节）；
2. 代码实现了但文档没写（野生行为，引用文件:行号）；
3. 描述不一致（数值、默认值、触发条件、边界行为）。

不要修改任何文件。对每条给出你的置信度与依据。
```

## P11 · 性能剖析

```
【系统名】上线后，大殖民地场景（60 居民 + 2 玩家 + 袭击中）出现 TPS 下降。
请定位原因，输出：
1. 热点清单（按每 tick 耗时排序，给出文件:行号与方法名）；
2. 每一处的复杂度与调用频率；
3. 具体优化建议（含预期收益与风险）；
4. 哪些优化是安全的，哪些会改变行为（需要先改 PRD）。

不要直接改代码，先给我分析。有不懂的可以问我。
```
