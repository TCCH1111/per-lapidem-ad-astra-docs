## 1. 一句话目标

让玩家能看到**每个居民现在缺什么、心情如何**，并让需求与我们的作息/禁区**发生可解释的冲突**——而不是"需求悄悄被满足"或"规则悄悄压过需求"。

**图层**：**L1 为主**。若必须改 `LivingPresence.urges` 的优先级或新增 `LivingNeed` 枚举值 → **L2**（小改，带 `// PLA:`）。

## 2. T0 已核实的契约（本轮实读，不是猜）

| 事实 | 位置 | 影响 |
| --- | --- | --- |
| 基底**已有需求机制**：`LivingNeed.BED/FOOD` | `plugins/person/living/LivingNeed.java`（enum，含 nameKey/icon） | **不需要从零造需求**；M2 是"在其上做张力与可见性" |
| 需求 → urge 的**唯一出口** | `LivingPresence.urges(who, colony)`（`:168`）产生 `EAT`/`SLEEP` | 想加新需求或改优先级，改这里（L2） |
| 需求带**权重语义** | `Urge.NOW`（紧急）/ `Urge.SPARE`；由 `hunger.urgent(level)` 决定 | 已有"急不急"的概念，可直接用于情绪张力 |
| 我们的**作息闸不拦需求** | `Standing` 只在 `Tours.unfit` 被问（派活时） | 需求走 urge，**不与作息竞争**——这是设计缺口：饿到快死也会准点收工 |
| 基底已有"居民卡片"需求条 | `SettlerNeed` + `LivingPresence.settlerNeeds(...)`（`:402`） | 玩家可见性比预想的好，**先看它已经给了什么**，别重复造 |
| 我们的只读面 | `BodyViews`（body）、`PresenceViews`（饥饿/床位）、`LaborViews`（退避）、`Explanation`（理由） | M2 可以直接用，不必再造管道 |

**结论**：M2 的第一件事不是"写需求系统"，而是**三件事**：
1. **补缺口**：需求与作息/禁区的冲突（现在需求不受作息约束）；
2. **补可见性**：把已有的饥饿/疲劳/心情读出来给玩家看（用 `PresenceViews` 扩展）；
3. **补解释**：需求与规则冲突时，**说清是谁压过谁**（延续 D8 的教训：不能互相冒充）。

## 3. 设计（三块，都可独立验收）

### 3.1 情绪：从需求推出"心情"，而不是新造一套
```
心情 = f( 饥饿水位, 疲劳水位, 最近是否被拒绝, 是否长期无活 )
```
- **纯函数**（与 `HoursPreset` 同款）：输入快照，输出枚举 + 数值，可无殖民地单测；
- 枚举先做 4 档：`CONTENT / WORRIED / STRESSED / DESPERATE`；
- 每档配**一句玩家能读的话**与**一条建议**（延续 `Explanation` 的做法）。

### 3.2 需求与规则的冲突（这是 M2 的"张力"本体）
- 现在：作息到点 → 停工；但**饿了仍会去吃饭**（需求走 urge，不受 `Standing` 约束）。
- 要做：**明确优先级**并让玩家可选：
  - `needs-first`（默认）：饿/困到阈值时，**允许越过作息**去做；
  - `rules-first`：规则压过需求，居民会忍到规则允许。
- **要点**：两种模式下，**玩家都能在书里读到"是规则挡着他吃饭"还是"他自愿忍"**——否则又是一次"说错话"。

### 3.3 可见性：把情绪接进书里
- 复用 `Billboard`/`Board`：居民行加一条情绪与原因；
- 复用已有的 `SettlerNeed` 卡片（先看它画了什么，缺什么补什么）。

## 6. 风险

| 风险 | 处理 |
| --- | --- |
| 情绪变成"又一套数字" | 每档必须能回答"玩家该做什么"；回答不了就不加这一档 |
| 需求优先级改动影响既有 703 测试 | 默认模式**保持现状**；新模式只在显式开启时生效 |
| 与上游 `SettlerNeed` 卡片重复 | N6 先读现有卡片，只补缺的，不重画 |
| 情绪衰减率引入不确定性 | 纯函数 + 固定输入，禁止读世界时钟以外的随机源 |
