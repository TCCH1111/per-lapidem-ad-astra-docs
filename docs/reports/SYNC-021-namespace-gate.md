---

## 1. 为什么值得单独做一条门禁

SYNC-015 那类 bug 的特征：

| 特征 | 后果 |
| --- | --- |
| 目录名是 modid 的一部分 | 改名时容易漏 |
| 代码按目录名拼 id | 漏了 → 资源**静默不加载** |
| 相关测试由 property 控制 | 默认套件跑不到 → 本地全绿 |
| 影响面 | 7 个雕刻图案在游戏里完全不存在 |

**"静默 + 默认不跑"= 只有专门的静态检查能抓到。**

---

## 2. 规则（刻意做窄）

> 若 `data/<ns>` 的名字以 `folkways` 或 `plaa` 开头，
> 那么它必须**恰好**是共享命名空间 `folkways`，或者**恰好**等于该模块的 `ext.modId`。

**为什么不做成"所有目录都要等于 modid"**：模块可以合法地为别的 mod 提供数据
（`mods/create/.../data/create/…`），一刀切会在那天立刻误报。
第三方命名空间（`create` / `minecraft` / `c`）**不在规则内**。

第二条测试更基础：**每个模块都必须声明 `plaa_*` 的 id**（防止新建模块忘了改名）。

---

## 3. 证明它能抓错（不是"它现在通过"）

| 步骤 | 结果 |
| --- | --- |
| 1. 把 `data/plaa_chiselsandbits` 临时改回 `data/folkways_chiselsandbits` | —— |
| 2. 跑 `npm run test:unit` | **`not ok 67`** · `pass 141 / fail 1`，点名该目录 |
| 3. 改回 `data/plaa_chiselsandbits` | —— |
| 4. 再跑 | **`tests 142 / pass 142 / fail 0`** |

**这条门禁复现了当初的事故，并且以正确的方式失败。**

---

## 4. 它跑在哪

| 位置 | 触发 |
| --- | --- |
| 本地 | `npm run test:unit`（`tests/**/*.test.ts` 自动包含） |
| CI | fork 的 `Build` 作业（第 11 步 `npm run test:unit`） |

**不需要额外接线**——它落在既有的 unit 门禁里。

---

## 5. 防退化

测试里断言 `checked >= 4`：如果哪天有人把扫描逻辑改坏（比如正则失效、目录结构变化），
门禁会**因为"检查得太少"而失败**，而不是静默通过。

> 一个永远通过的门禁不是门禁，是一个装饰。

## 7. 与 D17 的关系

D17 的结清条件是"每次同步后复查 Java 与 `data/` 里是否残留旧 modid"。
**现在 `data/` 的一半由 CI 自动复查**；Java 字符串那一半仍有 69 处历史教训，尚无同类静态检查。

**建议的下一步**（仍不需要你决策）：给 Java 源码加同样的门禁——
"源码里出现 `folkways_x:` 这类**带冒号的旧 modid 前缀**就失败"。
那正是 SYNC-015 里测试新旧名混用的成因。
